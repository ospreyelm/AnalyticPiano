HarmonyLab Legacy Exercise Formal Schema

Technical schema reference for legacy exercise payloads stored in Exercise.data, with parser normalization rules, grader routing, and generation/storage behavior.

Model: apps/exercises/models.py Parser: lab/static/js/src/models/exercise_definition.js Grader: lab/static/js/src/models/exercise_grader.js View payload assembly: lab/views.py Date: 2026-05-26
legacy writes frozen legacy rows readable new writes use UMTO factory
New non-UMTO rows are blocked by model validation unless HARMONYLAB_ALLOW_LEGACY_EXERCISE=1 is set.

1. Storage Contract

Layer Field Type Behavior
Django model Exercise.data JSON (RawJSONField) Holds the entire exercise payload for both legacy and UMTO rows.
Model guard Exercise.clean() Validation hook Blocks creation of non-UMTO new rows; allows existing legacy rows to continue saving.
Frontend entry ExerciseDefinition.parse(definition) Runtime parser Normalizes payload into internal exercise.problems and type-specific behavior.

2. Shared Legacy Envelope (Chord-Based)

Top-level keys

{
  "type": "matching|analytical|analytical_pcs|figured_bass|figured_bass_pcs|identification",
  "introText": "...",            // optional
  "reviewText": "...",           // optional
  "staffDistribution": "keyboard|...",
  "key": "jC_ | iA_ | h | ...",  // HarmonyLab key string
  "keySignature": "",            // optional
  "analysis": {
    "enabled": true,
    "mode": { "roman_numerals": false, "thoroughbass": false, ... }
  },
  "highlight": {
    "enabled": false,
    "mode": { "roothighlight": true, ... }
  },
  "chord": [ ... ],
  "timeSignature": "4/4",        // optional
  "semibrevesPerLine": 4          // optional
}

Chord item schema

{
  "visible": [60, 64, 67],    // required for most legacy play types
  "hidden": [72],             // required for most legacy play types
  "rhythmValue": "w|h|q|8|16|32",   // optional
  "unison_idx": 0,            // optional
  "notes": [60, 64, 67],      // optional input, parser recomputes normalized notes
  "answer": "V7",            // identification only
  "choices": ["I", "V", "V7"]  // identification only
}

3. Type: matching

AspectRuleSource
Input shapechord[i].visible + chord[i].hiddenLegacy parser
NormalizationKeeps visibility as given, computes notes = unique(visible + hidden)ExerciseDefinition.parse
GradingnotesMatch() exact MIDI matchExerciseGrader
 
{
  "type": "matching",
  "staffDistribution": "keyboard",
  "key": "jC_",
  "analysis": { "enabled": true, "mode": { "note_names": true } },
  "highlight": { "enabled": false, "mode": { "roothighlight": true } },
  "chord": [
    { "rhythmValue": "w", "visible": [60, 64, 67], "hidden": [] }
  ]
}

4. Type: analytical and analytical_pcs

AspectRuleSource
Input shapeSame as matching chord entriesLegacy parser
NormalizationFor each problem: visible=[], hidden=notesExerciseDefinition.parse
Gradinganalytical uses analysisMatch(); analytical_pcs uses analysisPcsMatch()ExerciseGrader
 
{
  "type": "analytical_pcs",
  "analysis": {
    "enabled": true,
    "mode": { "pitch_class": true }
  },
  "chord": [
    { "visible": [48], "hidden": [] }
  ]
}

5. Type: figured_bass and figured_bass_pcs

AspectRuleSource
NormalizationParser rewrites each problem to bass-led split: visible = notes.slice(0,1), hidden = notes.slice(1)ExerciseDefinition.parse
Gradingfigured_bass => figuredBassMatch(); figured_bass_pcs => figuredBassPcsMatch()ExerciseGrader
 
{
  "type": "figured_bass",
  "analysis": {
    "enabled": true,
    "mode": { "thoroughbass": true, "abbreviate_thoroughbass": true }
  },
  "chord": [
    { "visible": [48, 64, 67, 72], "hidden": [] }
  ]
}

6. Type: identification (legacy static chord ID)

AspectRuleSource
Input shapeEach chord carries notes, answer, choicesExerciseDefinition.parse
Normalizationvisible=notes, hidden=[], answer/choices retainedExerciseDefinition.parse
Feedback modeidentMode = submit | practice | testforms + lab view injection
GradingIdentificationGrader compares chosen label vs answer per slotidentification_grader.js
 
{
  "type": "identification",
  "identMode": "submit",
  "analysisType": "chord_quality",
  "inputMode": "dropdown",
  "chord": [
    {
      "notes": [60, 64, 67],
      "answer": "I",
      "choices": ["I", "ii", "IV", "V"]

  ]
}

AspectRuleSource
Score payloadUses CIR score with score.meta + score.measures[*].staves.*.voices[*].items[*]ExerciseDefinition.parse + score_timeline.js
ProblemsEmpty at parse time; timeline windows are derived from score eventsExerciseDefinition.parse
Settingsmode, targetVoices, display, grading, excerptforms.py chorale settings

10. Generation Path (Current vs Legacy)

Current production generation

management command -> build CIR / analysis overrides -> save_umto_exercise(...) -> Exercise.data (isUMTO=true)

Legacy generation status

Legacy exercise shapes remain readable and editable for grandfathered rows. New legacy rows are blocked by model guard and should not be generated in normal paths. One-shot migration scripts may use HARMONYLAB_ALLOW_LEGACY_EXERCISE=1.
