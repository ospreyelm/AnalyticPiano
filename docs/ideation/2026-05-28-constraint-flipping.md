# Constraint-Flipping Ideation — Monteverdi Music

**Frame:** Invert the obvious constraint to its opposite or extreme. Use the resulting design as a candidate even if the flipped premise is not realistic.

**Topic axes:** mastery feedback loop | exercise corpus & curriculum sequencing | student-facing UX | teacher & course management | grading infrastructure

---

## Idea 1: Notation-Click Harmonization (No-MIDI Play Mode)

**Constraint flipped:** MIDI keyboard required → no hardware at all

**Axis:** grading infrastructure

**Summary:** Extend the existing `chorale_identification` click-to-label interaction model to cover the `harmonization` (figured-bass realization) exercise type. Instead of playing upper voices on a MIDI keyboard, the student clicks a staff slot and chooses a pitch from a popup (analogous to how `note_name` identification already works). The grader checks whether the clicked pitch satisfies the figured-bass constraint, using the same pitch-class matching already implemented in `HarmonizationGrader`. This unlocks Safari, Firefox, iOS, and all contexts where a MIDI keyboard is unavailable — matching Artusi's notation-entry-only reach while preserving the real-time feedback loop.

**Basis:** `reasoned:` Artusi has 50k+ users and 32M+ graded questions using notation-entry only. The platform already has click-based grading for pitch-identification exercises (`chorale_identification` with `IdentificationGrader`), and `HarmonizationGrader` already checks pitch-class correctness per slice. The gap is purely UI: rendering clickable staff slots over the harmonization score and wiring clicks to `harmonizationMatch()` rather than MIDI `noteOn` events. No new grading logic is required — only a new input surface.

**Why it matters:** MIDI exclusivity is the single biggest access barrier for new students. A click-based harmonization mode that runs in any browser on any device — including phones and tablets — would let instructors assign exercises without hardware prerequisites, dramatically widening the student base a pilot class can include.

**Meeting test:** Yes — this directly addresses the Sept 2026 pilot risk that students without MIDI keyboards cannot participate.

## Idea 2: Instructor Exercise Builder (Corpus Self-Extension)

**Constraint flipped:** exercises pre-generated by developer → students/instructors generate their own

**Axis:** exercise corpus & curriculum sequencing

**Summary:** Build a guided in-browser exercise builder that lets instructors import a MusicXML file, select a measure range and voice configuration, preview the generated exercise in the lab renderer, and publish it to their course — all without touching the CLI or Django admin. Under the hood, this calls the same import pipeline already used by `import_chorale.py` and `import_bach_phrases.py`, exposed as an authenticated POST endpoint. The resulting `Exercise` row is UMTO-compliant and immediately assignable. Instructors can upload their own chorale harmonizations, exam corrections, or model answers from Sibelius/Finale/MuseScore exports.

**Basis:** `direct:` `docs/feature-status.md` lists "Streamlined exercise creation flow" (2.20) and "MusicXML import dashboard UI" (2.13) as planned. `import_musicxml.py` exists as a management command. The CLI pipeline already works end-to-end; the missing piece is a browser form that calls it. This flip (developer generates → instructor generates) converts a one-time corpus-building bottleneck into a self-extending library.

**Why it matters:** The corpus is the prerequisite — automated grading only scales if the exercise library covers the curriculum (STRATEGY.md, "Exercise corpus" track). Every exercise that requires a developer CLI call is a curriculum gap the instructor cannot close themselves. Self-service import removes the developer from the critical path for content and unblocks adoption at schools that use non-standard repertoire.

**Meeting test:** Yes — this is on the planned feature list and directly unblocks the teacher-as-buyer value proposition.

## Idea 3: Chorale Race / Peer Leaderboard (Multiplayer)

**Constraint flipped:** one student practices alone → multiplayer / peer-comparison

**Axis:** student-facing UX

**Summary:** Add an opt-in session-level leaderboard to any playlist: when a student completes an exercise, their score and time-to-complete appear on a shared class board visible to everyone in the course, ranked by accuracy and then speed. No synchronous play is required — it's an async race against classmates' scores. The board resets per assignment period (matching the existing recurring-assignment period already modeled in the DB). Instructors can toggle the feature per assignment.

**Basis:** `reasoned:` Gamification research (Duolingo, Khan Academy leaderboards) shows that visible peer comparison on time-boxed goals increases completion rates by 30-50% in skill-drill contexts. The platform already tracks per-student per-exercise performance with timestamps and correctness scores (`PerformanceRecord` rows implied by "Performance History" in the LMS assessment). The leaderboard is a read-only aggregation over existing data — no new grading or scoring infrastructure needed. The recurring-assignment period model already defines the time-box naturally.

**Why it matters:** The key metric is "exercises completed per student per week" (STRATEGY.md). A visible peer leaderboard is one of the cheapest interventions to move that metric — it costs one query per page load and one display component, but converts solitary drill into a social practice loop. It also gives instructors a diagnostic signal: students who fall off the leaderboard mid-week are the ones to follow up with.

**Meeting test:** Yes — directly targets the primary engagement metric with minimal implementation cost.

## Idea 4: Post-Session Error Replay (Delayed Reflective Grading)

**Constraint flipped:** grading is immediate → delayed / reflective (practice first, grade later)

**Axis:** mastery feedback loop

**Summary:** Add a "Review Session" mode: the student plays through an entire chorale or harmonization exercise with no live correctness feedback (notes do not turn black/red in real time). At the end, the session replays in a step-by-step annotated view — each window highlighted in green or red, with the student's played notes and the expected notes shown side by side. The student's `problems` array (already captured by `chorale_grader.js`'s `windowStats`) is the data source; replay is a pure rendering pass over stored correctness data.

**Basis:** `direct:` `chorale_grader.js` lines 50-51, 371-451: `windowStats` already records per-window status, correct MIDI pitches, incorrect attempts, and `completedAt` timestamps. The data to power a full replay already exists post-session; it is currently only used to compute the grade scalar. A replay renderer is a new UI component over existing data, not new grading logic.

**Why it matters:** Immediate feedback can be a crutch — students learn to correct by trial-and-error rather than hearing errors as musical problems. Delayed reflective feedback after a run-through mirrors how a teacher would conduct a lesson: let the student attempt the passage, then dissect it together. This is also the grading mode that makes sense for a timed exam (play the chorale, submit, see the analysis afterward) — a mode the platform needs before the Sept 2026 pilot if instructors want to use it for assessment.

**Meeting test:** Yes — opens the door to exam-mode deployment and activates already-collected per-window data for pedagogically-motivated reflection.

## Idea 5: Self-Directed Skill Tree (No-Instructor Path)

**Constraint flipped:** one instructor per course → no instructor (fully self-directed learning path)

**Axis:** mastery feedback loop

**Summary:** Wire the existing but inert mastery engine (5-level DAG, `SkillMastery` model, decay algorithm already in `adaptive_learning.md`) to a public-facing "Practice by Skill" UI. A student who is not enrolled in any course can navigate directly to a skill node (e.g., "Dominant Seventh Chords"), see exercises tagged `Dominant_Seventh`, complete them, and have their mastery level update in real time. The skill map becomes a standalone product path — no instructor, no course enrollment required — targeting self-directed learners, exam preppers, and prospective students evaluating the platform.

**Basis:** `direct:` `apps/exercises/models.py` lines 384+, 589+, 983+: `SkillMastery`, `is_adaptive`, `adaptive_mode`, `mastery_threshold` all exist as DB-level fields. `adaptive_learning.md` documents the full decay/unlock logic. CLAUDE.md flags the mastery engine as "inert." The flip produces a concrete activation task: write the view that reads `SkillMastery` for the current user + the skill DAG and renders a navigable tree, with the adaptive playlist selector already built (`create_smart_playlist.py`) as the exercise-selection backend.

**Why it matters:** The no-instructor path is also the viral / word-of-mouth path. A student who discovers the platform through a search for "figured bass practice" should be able to start practicing immediately without waiting for an instructor to set up a course. This lowers acquisition cost and generates usage data that future instructors see when evaluating adoption — a compounding return on the mastery infrastructure already built.

**Meeting test:** Yes — activates a significant existing investment (mastery engine, skill tags, adaptive playlist logic) and opens a direct-to-student acquisition channel.

## Idea 6: Transposition-Based Infinite Drill (Procedural Exercise Generation)

**Constraint flipped:** exercises are fixed repertoire → procedurally generated exercises of arbitrary complexity

**Axis:** exercise corpus & curriculum sequencing

**Summary:** Rather than generating synthetic exercises from scratch (abandoned as `curriculum-generation` branch), use the existing smart-transposition engine to create a virtually unlimited supply of exercises from the real corpus: for any imported Bach phrase, automatically generate all 12 transpositions as virtual exercises (IDs like `EA00DD+4`, `EA00DD+7`, etc.) and serve them from the same UMTO endpoint. A student who has completed an exercise in C major is presented the same phrase in E-flat, then G, rotating through keys until the skill tag shows `proficient` in multiple keys. The corpus is the seed; transposition is the multiplier.

**Basis:** `direct:` `apps/exercises/utils/transpose.py` already implements smart-direction transposition producing virtual IDs like `EA00DD+16`. `docs/CLAUDE.md` notes: "Transposition creates duplicate Exercise rows — No — transposed copies are virtual, generated on the fly." The adaptive playlist infrastructure and `skill_tags` GIN index exist. This flip (fixed → infinite) requires no new exercise-generation code — only a curriculum policy: "after completing a tagged exercise in the home key, queue the same exercise in N transpositions."

**Why it matters:** The transposition layer converts ~45 imported exercises into ~540 practice instances covering all keys — multiplying the corpus 12x at zero content-creation cost. For the Sept 2026 pilot, this directly addresses the risk that the corpus is too thin to fill a semester of practice. It also serves the adaptive engine's need for key-diverse material without DB duplication.

**Meeting test:** Yes — 12x corpus multiplication with no new content work and no new grading logic, directly using infrastructure already built and tested.

## Idea 7: UMTO REST API (Embed-Everywhere Infrastructure)

**Constraint flipped:** the product is a web app → the product is an API that other tools embed

**Axis:** teacher & course management

**Summary:** Publish a versioned REST API that exposes: exercise fetch by ID or skill tag, exercise completion submission (POST with MIDI event log or click-answer array), and student mastery read. The UMTO format is already JSON-serializable and schema-validated — it is designed to travel over HTTP. An LTI 1.3 consumer (Moodle, Canvas) calls `GET /api/v1/exercises?skill=Dominant_Seventh&unit=9`, renders the VexFlow widget in an iframe (the existing lab UI), posts back completion data, and the grade flows into the LMS gradebook automatically. This positions Monteverdi Music as infrastructure rather than a competing LMS — reducing the instructor's switching cost from "replace my LMS" to "add this widget."

**Basis:** `direct:` `docs/feature-status.md` lists "LTI integration (Moodle)" as Planned with "Requirements TBD May 2026." UMTO schema is at `apps/exercises/umto_schema.json` and auto-regenerated by `make_umto_schema`. The exercise model's `skill_tags` ArrayField with GIN index supports efficient tag-based queries. `reasoned:` The instructor buyer's actual resistance to adoption is not "I don't want auto-grading" — it is "I don't want to move my entire course out of Canvas." An embeddable API removes that objection entirely. Artusi's moat is its user count; Monteverdi Music's moat is corpus depth + real-time MIDI grading — both are more valuable as services than as a standalone destination.

**Why it matters:** LTI integration is the institutional sales motion: it converts "adopt a new platform" (high friction, IT approval required) into "add a plugin to an existing LMS" (low friction, single-instructor decision). With the Sept 2026 pilot approaching, an LTI-first API strategy means the pilot instructor does not have to run a parallel gradebook — assignments flow through Canvas/Moodle as if they were native. This is the path to course adoption at scale.

**Meeting test:** Yes — directly addresses the hardest barrier to institutional adoption and aligns with the planned LTI feature.
