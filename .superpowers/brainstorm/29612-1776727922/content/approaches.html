Three approaches to the student app

All three use Django + the existing data models. Differences are in scope and architecture.

A

Thin skin on existing lab

Add a new Django app (student/) with clean templates that wrap the existing exercise lab. Strip the header, hide dashboard links, add a unit progress sidebar. The exercise engine stays unchanged — same JS, same URLs, just different chrome.

Pros

  • Fastest to ship — days not weeks
  • Exercise engine already works
  • One codebase, no duplication

Cons

  • Current lab JS is RequireJS/jQuery — hard to extend cleanly
  • URL structure exposes lab internals
  • Instructor/student separation is CSS, not real
B

New student app with clean URLs + views (recommended)

New Django app student/ with its own URL namespace (/s/), templates, and views. Unit home, exercise player, progress API. Reuses existing models (Exercise, Playlist, StudentSkillMastery, PerformanceData) and embeds the existing exercise JS via iframe or direct include — but the surrounding page is fully student-focused.

Pros

  • Clean separation — student URLs never show dashboard
  • Proper auth: student role vs instructor role
  • Khan-style UX: unit home + auto-resume + skill mastery
  • Foundation for future mobile/PWA

Cons

  • 2–3 weeks to build well
  • Need to define student vs instructor auth clearly
C

Separate React SPA

Full React frontend, Django REST API backend. Student app is a standalone SPA at a subdomain (learn.harmonylab.com). Exercise player is reimplemented in React, pulling data from DRF endpoints.

Pros

  • Modern, fast, mobile-friendly
  • Clean API boundary — future-proof for native apps

Cons

  • Months of work — reimplements exercise engine
  • Two codebases to maintain
  • Overkill for a pilot

My recommendation: B — new Django app, clean student URLs, reuse existing engine and models. Ships in 2–3 weeks, looks nothing like the current dashboard, and sets up the right foundation for monetization later.
